# 평가

`questions.csv`의 질문 30개로 RAG 답변을 측정하고, 같은 질문으로 개선 전·후를 비교합니다.
README의 목표 지표 4가지(정답률·근거 일치율·모름 처리율·응답 시간)를 이 폴더에서 잽니다.

## 파일

| 파일 | 내용 |
| --- | --- |
| `questions.csv` | 평가 질문 30개와 정답 요약·근거 조문·근거 페이지 |
| `holdout.csv` | **새 질문 10개** — 개선 작업 중에는 보지 않고, 개선이 평가셋에만 맞춘 것인지 확인할 때만 씀 |
| `run_eval.py` | 질문셋을 돌려 답변·출처·응답 시간을 저장하고 지표를 계산 |
| `chunk_experiment.py` | 청크 설정 비교 실험용 DB 만들기 (문자 100·500·1000자). 결과는 [`REPORT.md`](REPORT.md) 3장 |
| `test_run_eval.py` | 판정·지표 계산 로직 테스트 (API 호출 없음) |
| `results/<시각>-<이름>/` | 실행 결과. `results.csv`(질문별 답변·인용 조문·실제 검색 질문·판정)와 `summary.md`(지표 요약) |

## 질문 유형 (30개)

| No | 유형 | 개수 | 설명 |
| --- | --- | --- | --- |
| 1~12 | 단순 사실 | 12 | 한 조문에 답이 있는 질문 |
| 13~21 | 비교·종합 | 9 | 여러 조문·법령을 합쳐야 하는 질문 |
| 22~26 | 표현 변형 | 5 | 법률 용어를 피하고 일상어로 묻는 질문 (예: 전차금 → "미리 당겨 받은 돈") |
| 27~30 | 문서에 없음 | 4 | 지식베이스에 답이 없어 "확인되지 않는다"고 답해야 정답 |

## 실행 방법

```bash
# 1. 질문셋 검사 — API 호출 없음, 비용 없음
#    근거 조문이 실제 DB 조각에 들어가는지와 그 페이지를 확인합니다.
python eval/run_eval.py --dry-run

# 2. 평가 실행 — OpenAI 비용 발생, .env의 OPENAI_API_KEY와 chroma_db/ 필요
python eval/run_eval.py --label v3
python eval/run_eval.py --label v3 --only 1,7,27   # 일부 질문만

# 3. results.csv의 '정답 채점' 칸을 채운 뒤 지표 다시 계산
python eval/run_eval.py --summarize eval/results/<폴더>/results.csv

# 판정 로직 테스트
python -m unittest eval/test_run_eval.py -v
```

- 실행 1회에 질문 30개 × LLM 호출 3번(질문 확장·근거 선별·답변)이 듭니다. 모델은 `gpt-4o-mini`입니다.
- 질문 하나가 실패해도 나머지는 계속 측정하고, 실패 내용은 `오류` 칸에 남깁니다.

## 새 질문으로 확인하기 (`holdout.csv`)

`questions.csv` 결과를 보면서 프롬프트를 고치면, 점수가 평가셋에만 맞춰질 수 있어요.
그래서 **평가셋에 없는 질문 10개**를 따로 두고, 개선 후 점수가 여기서도 유지되는지 봐요.

```bash
python eval/run_eval.py --questions eval/holdout.csv --label holdout-<이름>
```

- 단순 사실 3 · 비교·종합 2 · 표현 변형 2 · 문서에 없음 3
- H3(일하다 다쳐 치료 중 해고)은 산재와 가까운 주제지만 답이 있는 질문이에요. 환각을 막으려다 정상 질문까지 거절하는지 잡아내려고 넣었어요.
- **이 질문들을 보고 프롬프트를 고치지 마세요.** 고치는 순간 더 이상 '새 질문'이 아니에요.

## 질문셋 작성 규칙 (`questions.csv`)

| 열 | 쓰는 법 |
| --- | --- |
| 질문 | 대상 사용자(알바·사회초년생·계약직·일용직)가 실제로 물어볼 말투로 씁니다. |
| 정답 요약 | 문서 기준 정답을 한두 문장으로. 예외·조건이 있으면 함께 적습니다. |
| 근거 조문 | `법령명 조문` 형식, 여러 개면 `;`로 구분. **첫 번째가 핵심 조문**입니다. 법령명은 PDF 파일명 앞부분과 같게 씁니다 (예: `근로자퇴직급여 보장법 제8조`). 문서에 없음 질문은 비웁니다. |
| 근거 페이지 | PDF 뷰어에 보이는 페이지 번호 (예: `근로기준법 p.3; 근로기준법 시행령 p.10`). |
| 비고 | 채점할 때 주의할 점 (예: 문서에 없는 수치를 단정하면 오답). |

질문을 고친 뒤에는 `--dry-run`으로 근거 조문이 DB 조각에 있는지 꼭 확인합니다.

## 판정 기준

**자동 판정** (`run_eval.py`)

| 열 | 값 | 기준 |
| --- | --- | --- |
| 근거 일치 | O / X / - | 답변 아래 출처 목록에 **핵심 조문**(근거 조문의 첫 번째)이 있으면 O. 문서에 없음 질문은 - |
| 모름 처리 | O / X / - | 문서에 없음 질문: "확인되지 않습니다/확인하지 못했습니다"라고 답하면 O, 답을 지어내면 X. 답이 있는 질문에서 거절하면 X(지나친 거절), 아니면 - |
| 첫 글자(초) / 전체(초) | 숫자 | 첫 글자가 나올 때까지 / 출처까지 다 나올 때까지 걸린 시간 |

**사람 채점** (`정답 채점` 칸)

| 표기 | 의미 | 점수 |
| --- | --- | --- |
| ✅ | 정확 | 1 |
| △ | 부분 정답 (조건·예외 누락 등) | 0.5 |
| ❌ | 오답·환각 | 0 |

- 모델 답변은 매번 조금씩 달라질 수 있으므로 한 사람이 같은 기준으로 채점합니다.
- 틀린 이유는 `비고`에 적어 두면 실패 사례 분석에 그대로 씁니다.

## 개선 전·후 비교

자세한 단계별 비교와 실패 사례는 [`REPORT.md`](REPORT.md)에 있어요.

- **개선 전**: 수업 기본 코드(첫 커밋 `b34bbdb`, chunk 100 / overlap 20)와 그때 방식으로 만든 DB(`chroma_db_backup_v1`)로 측정
  ```bash
  python eval/run_eval.py --system baseline --db-dir chroma_db_backup_v1 --label before
  ```
  - `chroma_db_backup_v1/`은 git에 없어요. 첫 커밋 방식(100자 단위)으로 만든 DB를 이 이름으로 두면 돼요.
- **개선 후**: 기능 개선이 반영된 코드(#33 기준)로 같은 질문을 측정
- 여러 결과를 한 표로: `python eval/compare.py 개선전=eval/results/<폴더> 개선후=eval/results/<폴더>`
- 청크 설정 비교: 실험용 DB를 만들고(임베딩 비용 발생) 같은 질문으로 평가
  ```bash
  python eval/chunk_experiment.py --dry-run     # 조각 수만 세기 (API 호출 없음)
  python eval/chunk_experiment.py char500       # chroma_db_chunk_char500/ 만들기
  python eval/run_eval.py --db-dir chroma_db_chunk_char500 --label chunk-char500
  ```

| 지표 | 목표 | 개선 전 | 개선 후 |
| --- | --- | --- | --- |
| 정답률 | ≥ 80% | 41.7% | **90.0%** |
| 단순 사실 (/12) | | 5.5 | 11.5 |
| 비교·종합 (/9) | | 4 | 8 |
| 표현 변형 (/5) | | 2 | 4.5 |
| 문서에 없음 (/4) | | 1 | 3 |
| 출처 정확도 (근거 일치율) | ≥ 90% | 0% (출처 표시 없음) | **96.2%** |
| 모름 처리율 | 100% | 25% | 75% |
| 평균 응답 시간 | ≤ 10초 | 3.3초 | 4.3초 |
| 새 질문 10개 정답률 | | 45% | **100%** |

정답 채점은 초안이에요 (QA 검토 후 확정).
